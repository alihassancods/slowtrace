Overly Permissive CORS Configuration

Medium Fixed
File
backend/src/api/main.py line 27
Vulnerability
allow_methods=["*"] and allow_headers=["*"] permitted any HTTP method (DELETE, PUT, PATCH…) and any request header from the allowed origin. For a read-heavy SSE API this is far wider than required.
Fix Applied
-    allow_methods=["*"],
-    allow_headers=["*"],
+    allow_methods=["GET", "POST", "OPTIONS"],
+    allow_headers=["Content-Type", "Accept", "Authorization", "Cache-Control"],

No Input Validation on Connection String — /connections/test

High Fixed
File
backend/src/api/connections.py line 30
Vulnerability
Any arbitrary string was accepted as a connection string with no length cap or format check. An attacker could supply an oversized payload or a non-DSN value that causes unexpected behaviour in asyncpg.
Fix Applied
+   @field_validator("connection_string")
+   @classmethod
+   def validate_connection_string(cls, v: str) -> str:
+       v = v.strip()
+       if len(v) > 2048:
+           raise ValueError("Connection string is too long (max 2048 characters).")
+       if not v.startswith(("postgresql://", "postgres://")):
+           raise ValueError(
+               "Connection string must start with 'postgresql://' or 'postgres://'."
+           )
+       return v

Raw Exception Detail Leaked in HTTP 502 & SSE Error Responses

Medium Fixed
File
backend/src/api/fixes.py lines 111, 119, 228
Vulnerability
Raw Exception strings were interpolated directly into HTTPException(detail=…) and SSE "error" events and returned to clients. This can expose internal hostnames, file paths, driver version strings, and PostgreSQL error codes.
Vulnerable Code
-    except Exception as exc:
-        raise HTTPException(status_code=502, detail=f"Database connection failed: {exc}")
-    except Exception as exc:
-        raise HTTPException(status_code=502, detail=f"Query fetch failed: {exc}")
-    except Exception as exc:
-        yield _sse("error", {"message": f"Database connection failed: {exc}"})
Fix Applied
+    except asyncpg.InvalidPasswordError:
+        raise HTTPException(status_code=502, detail="Database authentication failed.")
+    except asyncpg.InvalidCatalogNameError:
+        raise HTTPException(status_code=502, detail="Database not found.")
+    except OSError:
+        raise HTTPException(status_code=502, detail="Database host not reachable.")
+    except Exception:
+        raise HTTPException(status_code=502, detail="Database connection failed.")
5

Database Password Reflected in API Response Bodies (Legacy Routes)

High Fixed
Files
dashboard.py, health.py, explain.py, fix.py
Vulnerability
Legacy routes accept the DSN as a URL path segment and echo it back verbatim in the JSON response body as the connection_id field. Any DSN containing a password (e.g. postgresql://user:secret@host/db) was returned to the caller in cleartext.
Vulnerable Code
-    dsn = unquote(connection_id)
-    return DashboardReport(connection_id=dsn, ...)
Fix Applied
+   def _redact_dsn(dsn: str) -> str:
+       return re.sub(r"(://[^:@/]*:)[^@/]+(@)", r"\1***\2", dsn)
+
+   safe_id = _redact_dsn(dsn)
+   return DashboardReport(connection_id=safe_id, ...)
Same helper added to health.py, explain.py, and fix.py.
6

Fix History Endpoint Returns All Records Regardless of Caller

Medium Fixed
File
backend/src/api/fixes.py — GET /api/fixes/history/{connection_id}
Vulnerability
The endpoint validated that the supplied connection_id existed but then returned the full fix_history.json — all fix records for all connections — to the caller. In a multi-user or multi-database scenario this is an information disclosure vulnerability.
Vulnerable Code
-    return _load_history()   # returns ALL records
Fix Applied
+   history = _load_history()
+   scoped = [r for r in history if r.get("connection_id") == connection_id]
+   return scoped if scoped else [r for r in history if "connection_id" not in r]
